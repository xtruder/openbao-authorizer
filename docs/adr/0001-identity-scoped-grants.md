# Requester access is granted to the Requester's identity before use

A **Requester** asks for **Permission Items** ahead of use, and an **Approver** decides each item. Every approved item becomes a **Grant**: one `path` block, carrying OpenBao's own `expiration`, in one ACL policy per scope. A session Grant goes to the Requester's policy `agent-grant-<entity id>`, attached to its identity entity; project and global Grants go to policies the Requester's token carries from the moment it is minted (ADR-0006). OpenBao evaluates token and identity policies on every request, so the Requester's existing token gains access at once. Agents, bao-cred and tools such as secretspec keep using one token. One approval covers repeated use and batches of paths.

## Considered options

- **OpenBao control groups.** Every protected request needs its own approval, and the requester has to hold a wrapping token and unwrap the deferred response. That is too rigid for agents that read the same credentials repeatedly or need several paths for one task.
- **A new token per approval.** The approval would be scoped to one token, but agents and their tools would have to swap tokens mid-task.
- **One policy per Grant.** Approving, revoking and expiring Grants would be independent, but a batch of N approvals would cost N policy writes and N entity updates. Partial failures could leave some items granted and others not. OpenBao lets one policy repeat a path with different expirations, and each block lapses on its own, so a single policy per scope loses nothing.
- **One identity group per Grant or per Requester.** The authorizer's token could then be scoped by group name. Attaching the policy to the Requester's entity creates fewer objects. As a result the authorizer's token has `update` on `identity/entity/id/*`, limited to the `policies` parameter. OpenBao 2.7 can't restrict which names go into that list: `allowed_parameters` value globs reject JSON lists and accept a comma-joined string.
- **A shared AppRole identity.** AppRole maps every login of one role to a single entity, so grants would leak across unrelated work. Instead, **Named Tokens** are minted through a token role with one entity alias per **Named Identity** (ADR-0005).

## Consequences

- **Grants outlive any single token.** A newly minted Named or Session Token keeps its identity's unexpired Grants.
- **Every Grant has an expiry, and OpenBao enforces it.** Each block lapses independently, even while the authorizer is down, and the policy expires with its last block. Once a Grant expires, using that path again needs a new approval.
- **A batch of decisions is all-or-nothing.** It costs one policy write per scope it touches, followed by one database commit. A session policy's name is attached to the entity on the first approval and never detached, so revocation and expiry cost no entity writes. Policies are HCL, because JSON can't repeat a path.
- **Requester Rules decide who may file requests; Named Identities are the main kind of Requester.** The authorizer accepts a bearer token only when `lookup-self` reports an entity and the token matches an operator-defined rule: a token role, such as `named-identity`, or the auth mount it was issued from, such as an AppRole mount for CI. Grants land on the matched token's entity whatever its kind. Only humans allowed to mint can use that role, and the role pins the token's entity alias, so authentication needs no entity read. An auth-mount rule admits every token of that mount, so such a mount must serve Requesters only.
- **An Approver never decides their own request.** An identity can be both a Requester and an Approver, for example an AppRole that also carries the approver policy. Deciding is refused with `SELF_APPROVAL` when the Approver's entity filed the request, so nobody grants themselves access. Revoking stays open to every Approver, because it only removes access.
- **Requesters see the full catalog of Grantable Rules.** Every Requester sees every rule, its description and, for rules where the operator opts in with `discover`, the concrete names the authorizer lists with its own token, such as GitHub permission sets. Names are no secret here; the authorizer's policy then needs `list` on each discover path.
- **The authorizer's OpenBao token can grant privileges.** It writes Grant policy content and can attach any non-root policy to any entity, so it must be protected like an administrative credential. The **Hard Denylist** and **Grantable Rules** are enforced by the authorizer, not by OpenBao.
- **The threat model guards against agent mistakes, not a malicious agent.** The agent runs as the same OS user as the human who mints Named Tokens, so it can mint a token for any name and use that identity's Grants.
