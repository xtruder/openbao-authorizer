# Agents get access through Named Identities and Agent Sessions that bao-cred mints and stores

Agents get OpenBao access through **Named Identities**. A human who is logged in to OpenBao runs `bao-cred init` in a project (or `bao-cred auth <name>`), which mints a **Named Token** through the `named-identity` token role with entity alias `<name>` and stores it locally; a committed `.bao-identity` file at the git root names the project's identity, so every agent, tool and shell in the project uses it without any environment variable. Inside an agent conversation, detected from `BAO_SESSION_ID` or opencode's `OPENCODE_SESSION_ID`, bao-cred mints a **Session Token** from the Named Token on first use, so each **Agent Session** is a Requester of its own. The agent integration is a plain skill that works in any agent harness, with no plugin or minting service.

Grants attach to identities and Grant policies, not tokens (ADR-0001, ADR-0006), so stored tokens are only caches: minting a new one keeps every Grant, and losing one costs a re-mint.

## Decisions

- **Minting Named Tokens.** The human's `bao login` token (`~/.vault-token`) calls `auth/token/create/named-identity`, which a human policy allows. The role is `orphan`, so the Named Token outlives the human's token, and allows any alias (`allowed_entity_aliases = "*"`): any human who may mint may mint any name. The token's `meta.identity` names the Requester for Approvers.
- **Minting Session Tokens.** The Named Token calls `auth/token/create/agent-session`, which its baseline policy allows, with alias `<name>.<session id>` and `meta.session`. Session Tokens are its children, so rotating or revoking the Named Token revokes every session; the next command re-mints for the same alias, so the session keeps its Grants. A subagent has a session ID of its own and so its own Agent Session: bao-cred doesn't ask the agent harness which session is the parent. `BAO_NO_SESSION` turns sessions off.
- **Policies on the token.** Both roles mint tokens with their baseline policy, named like the role, plus `agent-grant-project-<name>` and `agent-grant-global` (`allowed_policies_glob`); ADR-0006 explains why.
- **Lifetime.** Named Tokens are periodic with a 768h (32-day) period: OpenBao caps a role's period at the token mount's `max_lease_ttl`, 768h by default, and raising it would lengthen every token on the mount. Session Tokens have a 24h period. bao-cred renews a Session Token once less than half its period is left, and the Named Token whenever it mints or renews a session, and in `env` and `status`, so active projects and sessions never expire. secretspec never renews, which is fine: Grants are short-lived anyway.
- **Rotation.** `bao-cred auth` always mints a new Named Token and revokes the previous one, so it doubles as recovery from a leaked token. `bao-cred logout` revokes and deletes it; Grants stay until they expire.
- **Storage.** One token store holds both kinds. Named Tokens go to the OS keyring (service `bao-cred`, account `<name>`) when it answers, else to a `0600` file `$XDG_STATE_HOME/bao-cred/<name>.token`, with a warning. The keyring is probed once per command, on first use, with a 5-second timeout, so a locked keyring waiting on an unlock prompt counts as unavailable. A non-secret `index.json` records which store holds each Named Token: a token in a keyring that is now locked is reported with a hint instead of looking missing, and a stale keyring copy left while it was locked never shadows a newer file. Session Tokens, one per conversation, always go to files under `sessions/<name>/`; files untouched for 48 hours are pruned. The keyring address is stable so that other tools, such as a secretspec keyring credential, can read it directly.
- **Project file.** `.bao-identity` at the nearest directory holding `.git` (a directory, or a file in worktrees) contains only the name, so it is committed and every clone and worktree shares it. A file, unlike an `.envrc` variable, needs no direnv and reaches agent shells that don't load `.envrc`. Its presence selects an identity, which is what stops the fall back to the human's token.
  - *Amended:* lookups take the nearest `.bao-identity` in the working directory or any parent, past git roots; `bao-cred init` still writes it at the git root. A file in a parent directory, such as the home directory, selects an identity explicitly for everything below it, for example the human's own ssh through the credential helper. We chose this over an implicit identity derived from the `bao login` token, which would make requests under an identity nobody named.
- **Lookup order.** `BAO_TOKEN`, `VAULT_TOKEN`, then the token of `--identity`, `BAO_IDENTITY` or `.bao-identity` (the Session Token inside an Agent Session, else the Named Token), then `~/.vault-token` unless `BAO_NO_TOKEN_FILE` is set. A selected identity without a stored token is an error. An explicit token always wins.
- **Handing tokens to other tools.** `bao-cred run -- <command>` gives one command `BAO_TOKEN` and `VAULT_TOKEN`; `bao-cred env` prints them for `.envrc`. Both resolve the token as above, for tools that read only the environment: the `bao` CLI, and secretspec, which otherwise falls back to `~/.vault-token`.

## Considered options

- **A `.env` file in the project.** Easy to commit by mistake, copied stale across worktrees, and read by agents that glob project files.
- **Storing the token in secretspec.** With the OpenBao provider it needs a token to fetch the token; with the keyring provider every project's `secretspec.toml` must declare it. secretspec can still read bao-cred's keyring entry by reference.
- **An agent-harness plugin that injects each conversation's token.** It ties access to one harness, needs a minting credential running beside the agent, and depends on harness internals to route each command its token. Reading the harness's session ID from the environment gives the same per-conversation identity with bao-cred alone.
- **Resolving a subagent to its parent session.** opencode records the parent, but reaching it needs its server address and password or its internal database. Subagents simply start without their parent's session Grants; project and global Grants still reach them.
- **Session Tokens in the keyring.** One entry per conversation would flood it, and they live a day.

## Consequences

- **Anyone who mints a name shares its project Grants**, for example a collaborator whose clone carries the same `.bao-identity`. Scoping names per human is the fix if more people mint.
- **The human's shell in that directory acts as the Named Identity too.** Administrative `bao` commands there need the human's token explicitly.
- **Agents can reach the human's token and any project's.** They run as the same OS user and can read `~/.vault-token`, and a Named Token may mint Session Tokens carrying another project's Grant policy, because OpenBao can't restrict the policy names in a token request beyond the role's glob. The threat model guards against agent mistakes, not a malicious agent.
